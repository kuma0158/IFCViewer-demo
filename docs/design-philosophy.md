# 設計思想 — IFC Viewer Pilot

このドキュメントは、IFC Viewer Pilot が「なぜこの形になっているか」をまとめたものです。
バックエンド・フロントエンドそれぞれの設計思想の詳細は [design-backend.md](design-backend.md) / [design-frontend.md](design-frontend.md)、
個々のファイルや関数の説明は [backend.md](backend.md) / [frontend.md](frontend.md) を参照してください。

## 1. このシステムの位置づけ

**目的は「IFC を開いて、3D で見て、部材をクリックすると属性が分かる」ことを最小構成で実証すること**です。
本番システムではなく **パイロット（技術検証）** として作られており、すべての判断は次の優先順位に従っています。

1. **動くことを最短で確認できる**（セットアップが単純、起動手順が短い）
2. **読んで理解できる**（コード量が少なく、仕組みが追える）
3. **本番化するときの差し替えポイントが明確**（簡略化した箇所を隠さず書き残す）

性能・永続化・認証・大規模モデル対応は、意図的に後回しにしています（[7. 意図的に割り切っていること](#7-意図的に割り切っていること)）。

## 2. 段階的に積み上げる（Step 方式）

システムは一度に作らず、検証できる単位で段階的に積み上げています。

| Step | 成果物 | 確認したこと |
|---|---|---|
| Step 1 | `analyze_ifc.py`（CLI） | ifcopenshell で IFC から階・種類・プロパティセットを取り出せるか |
| Step 2 | `backend/`（FastAPI） | 同じ解析を Web API として提供できるか |
| Step 3〜4 | `frontend/`（Vue 3 + TS + Three.js + web-ifc） | ブラウザで 3D 表示し、クリックした部材と API の属性を結び付けられるか |
| Step 5 | `frontend/` を純粋な TypeScript に置き換え（Vue を撤去） | フレームワーク無しでも同じ層分離を保てるか・依存を減らせるか |

各 Step は前の Step の成果をそのまま土台にしています（Step 1 の解析ロジック → Step 2 の `ifc_service.py`）。
「前の段階が動いている」ことを確認してから次に進むため、問題が起きたときに原因の切り分けが容易です。

## 3. 中心となるアイデア：expressID を共通キーにする

このシステムで最も重要な設計判断です。

```
           IFC ファイル内の番号  #123  (= expressID)
                 ┌──────────┴──────────┐
   サーバー: ifcopenshell             ブラウザ: web-ifc
   el.id() == 123                     flatMesh.expressID == 123
   → 属性・プロパティセット            → 三角形メッシュ（mesh.userData.expressID）
```

- IFC ファイル内の行番号 `#123` は、**ifcopenshell でも web-ifc でも同じ値**になる。
- そのため、ブラウザ側で「クリックした Mesh の `userData.expressID`」を取り出し、
  `GET /api/models/{modelId}/elements/{expressId}` に渡すだけで属性が取れる。
- 独自の ID 変換表や対応付けの仕組みを一切作らずに、**形状（ブラウザ）と属性（サーバー）を疎結合のまま結べる**。

この発想があるから、後述の「解析をサーバーとブラウザで分担する」構成が成り立っています。

## 4. 役割分担：得意なものに得意なことをさせる

| 担当 | ライブラリ | 役割 | 理由 |
|---|---|---|---|
| サーバー | ifcopenshell（Python） | 集計・属性（プロパティセット）取得 | 属性・空間構造の取り扱いが成熟しており、Python で書きやすい |
| ブラウザ | web-ifc（WebAssembly） | 形状 → 三角形メッシュ生成 | 重い形状処理をクライアントで行い、メッシュをサーバーから転送しなくて済む |
| ブラウザ | Three.js | 描画・視点操作・クリック判定 | WebGL の定番。Raycaster でピック処理が簡単 |

結果として **同じ IFC をサーバーとブラウザで 2 回解析** しています。
効率は最善ではありませんが、それぞれのライブラリを標準的な使い方のまま使えるため、
構成が単純でパイロットとしての分かりやすさを優先しました（frontend.md「二重の解析」参照）。

## 5. 関心の分離

### バックエンド：HTTP と IFC を分ける

| ファイル | 扱うもの | 扱わないもの |
|---|---|---|
| `main.py` | リクエスト検証、ステータスコード、ファイル保存、モデル保持 | ifcopenshell の呼び出し詳細 |
| `ifc_service.py` | IFC の読み込み・集計・部材詳細 | HTTP（`HTTPException` 等を知らない） |

`ifc_service.py` は HTTP に依存しない純粋な関数（`dict` / `None` を返す）なので、
CLI やテストからそのまま再利用できます。「見つからない」は `None` で返し、それを 404 に変換するのは `main.py` の責務です。

### フロントエンド：画面・3D・変換・通信を分ける

| ファイル | 責務 |
|---|---|
| `app.ts` | 画面全体の状態（モデル・選択中の部材・ステータス・エラー）と DOM 描画 |
| `viewer/IfcViewer.ts` | 3D の表示・操作・選択。**API を知らない**（`load(url)` で読み込み、`onSelect` / `onLoaded` / `onError` コールバックで通知するだけ） |
| `lib/ifcLoader.ts` | web-ifc の出力 → Three.js Mesh への変換（DOM・画面を知らない純粋関数） |
| `api.ts` | バックエンド呼び出し |
| `types.ts` | API レスポンスの型（バックエンドとの契約） |
| `lib/ifcLabels.ts` | 表示用の日本語ラベル |

ビューアは「URL を渡されたら表示し、クリックされたら番号を通知する」部品に徹しているため、
属性の取得方法や表示方法を変えてもビューアには手を入れずに済みます。

## 6. 利用者に寄り添う

技術検証であっても、触る人（BIM に詳しくない人を含む）が迷わないことを重視しています。

- **原因が分かるエラーメッセージ**
  IFC が開けないとき、`describe_open_error()` がファイル先頭を見て「ZIP です」「HTML を保存しています」「UTF-16 です」などの
  **対処方法つきの日本語メッセージ** を返します。
  判定は **ifcopenshell で開くのに失敗したときだけ** 行うため、読めるファイルを誤って弾くことはありません。
- **日本語ラベル + 元の英語名の併記**
  `IfcWall → 壁`、`IsExternal → 外部に面する` のように日本語で表示しつつ、元の英語名も小さく／ツールチップで残します。
  辞書に無い名前は英語のまま表示し、**表示が欠けることはない**（フォールバック）設計です。
- **自然な操作感**
  ドラッグ（視点操作）とクリック（選択）を移動量 4px で区別し、誤選択を防ぎます。
  1 部材が複数 Mesh で構成されていても、同じ expressID の Mesh をまとめてハイライトします。
- **「対象外」も状態として表す**
  空間（`IfcSpace` など）は形状はあるが部材ではないため API は 404 を返します。これをエラーではなく
  「#123 は属性表示の対象外です」という正常な表示状態として扱います。

## 7. 意図的に割り切っていること

パイロットとして **「やらない」と決めていること** と、本番化時の差し替え先です。
簡略化は隠さず、コメントやドキュメントに明記する方針です。

| 割り切り | 現状 | 本番化の方向性 |
|---|---|---|
| 永続化 | 解析済みモデルはプロセスのメモリ（`_models` 辞書）。再起動で消える | DB / キャッシュ（Redis 等）/ オブジェクトストレージ |
| ファイルの後始末 | モデルの破棄（最大 20 件）・再起動と同時に削除 | ストレージのライフサイクル管理 |
| 認証・認可 | なし（`modelId` を知っていれば誰でも参照可） | ユーザー認証とモデル単位のアクセス制御 |
| 解析の非同期化 | スレッドプールで実行（他の利用者は待たない）。本人は解析完了まで待つ | バックグラウンドジョブ化 |
| サイズ上限 | 100MB、書き込み中に判定して打ち切り | アップロード前の事前検証・より細かい上限 |
| 大規模モデル | 1 部材 1〜複数 Mesh、描画コールが多い | ジオメトリのマージ・インスタンシング |
| 対応形式 | テキスト形式（STEP）の `.ifc` のみ | IFC-ZIP / ifcXML への対応 |

## 8. 型でバックエンドとフロントエンドの契約を守る

- `frontend/src/types.ts` は `backend/ifc_service.py` の戻り値と 1 対 1 で対応させた **API の契約書** です。
  キー名を変えたら両方を直す、というルールをコメントに明記しています。
- `tsconfig.json` は `strict: true`。`npm run build` は `tsc --noEmit` が通らなければビルドしません。
- 状態は型で表現します。例：選択中の部材は `ElementDetail | NotFoundElement | null` として、
  「未選択」「対象外」「属性あり」の 3 状態を描画処理（`renderSide()`）で型安全に分岐します。
- TypeScript は `~5.9.3` に固定（Step 4 で vue-tsc のために固定したバージョンを、動作確認済みとしてそのまま使用）。**動作確認済みのバージョンを固定し、理由を残す** 方針です。

## 9. 開発・運用のしやすさ

- **同一オリジンに見せる**：Vite のプロキシで `/api` を FastAPI に転送するため、フロントのコードは相対パス `/api/...` だけで書けます（CORS 設定はあくまで保険）。
- **セットアップを自動化**：`npm install` の `postinstall` で `web-ifc.wasm` を `public/` にコピーし、手作業を減らしています。
- **何度実行しても安全な起動スクリプト**：`scripts/start-servers.ps1` は待ち受け中のポートには触らない冪等な作りで、タスクスケジューラから定期実行して常駐させられます。
- **API を単体で試せる**：FastAPI の Swagger UI（`/docs`）から、フロントエンド無しで各 API を確認できます。

> 補足：バックエンドのポートは、別プロジェクトとの衝突回避のため `8001` を使っています（`vite.config.ts` / `start-servers.ps1`）。

## 10. まとめ

| 原則 | 具体例 |
|---|---|
| 最小構成で実証する | パイロットと割り切り、永続化・認証は後回し |
| 段階的に積み上げる | Step 1（CLI）→ Step 2（API）→ Step 3〜4（3D）→ Step 5（フレームワーク撤去） |
| 共通キーで疎結合に結ぶ | expressID で形状（web-ifc）と属性（ifcopenshell）を接続 |
| 得意なものに任せる | 属性はサーバー、形状はブラウザ |
| 関心を分離する | `main.py` / `ifc_service.py`、ビューアは API を知らない |
| 必要以上の道具を持たない | 画面が小さいのでフレームワークを使わず、DOM API と TypeScript で書く |
| 利用者に寄り添う | 原因別の日本語エラー、日本語ラベル + 英語併記 |
| 割り切りを隠さない | 簡略化した箇所と本番化の方向性を明記 |
| 型で契約を守る | `types.ts` と strict な型チェックをビルドの前提に |
