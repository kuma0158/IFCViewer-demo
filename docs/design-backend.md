# バックエンドの設計思想（FastAPI + ifcopenshell）

全体の設計思想は [design-philosophy.md](design-philosophy.md)、ファイル・関数単位の解説は [backend.md](backend.md) を参照してください。
このドキュメントは、バックエンドが **なぜこの形になっているか** を掘り下げたものです。

## 1. バックエンドの役割：「属性の正本」

バックエンドは IFC の **属性（意味情報）** を担当し、**形状（3D）は担当しません。**

| バックエンドがやること | バックエンドがやらないこと |
|---|---|
| IFC を受け取り、保存し、ifcopenshell で開く | 三角形メッシュの生成・送信 |
| 階・種類ごとの集計、部材一覧の作成 | 描画・視点・選択の管理 |
| 部材 1 件の基本情報とプロパティセットの返却 | 日本語ラベルへの変換（表示はフロントの責務） |
| 元の IFC ファイルをそのまま返す | 形状の変換やファイル形式の変換 |

形状はブラウザの web-ifc に任せ、サーバーは元ファイルを **加工せずに** 返すだけにしています。
こうすると、サーバーは重いジオメトリ処理（ifcopenshell.geom）を持たずに済み、依存もコードも小さく保てます。
両者は IFC 内の番号 `#123`（**expressID**）でつながるため、サーバーが「どのメッシュがどの部材か」を知る必要もありません。

> 形状生成をサーバーへ移す（メッシュを配信する）構成は、役割分担そのものを変える判断なので、行う場合は事前に合意を取る方針です。

## 2. 2 層構造：HTTP 層と IFC 層

```
            HTTP の世界                         IFC の世界
 ┌──────────────────────────────┐    ┌──────────────────────────────┐
 │ main.py                      │    │ ifc_service.py               │
 │  ・入力の検証（拡張子・サイズ）│───▶│  ・open_model()              │
 │  ・ステータスコードの決定      │    │  ・summarize()               │
 │  ・ファイル保存・後始末        │◀───│  ・element_detail()          │
 │  ・モデルの保持（_models）     │    │  ・describe_open_error()     │
 └──────────────────────────────┘    └──────────────────────────────┘
        FastAPI を知っている               FastAPI を知らない
```

### 境界のルール

- `ifc_service.py` は **FastAPI・HTTPException を import しない。** 戻り値は JSON にできる `dict` / `list` / `str` / `None` だけ。
- 「見つからない」は例外ではなく **`None` を返す。** それを 404 に変換するのは `main.py` の責務。
- 「開けない」の原因説明（`describe_open_error()`）は IFC の知識なので `ifc_service.py` 側に置き、ステータスコード 422 を付けるのは `main.py` 側。

### なぜ分けるのか

1. **再利用できる。** `ifc_service.py` は Step 1 の CLI（`analyze_ifc.py`）を API 向けに整理したもの。HTTP に依存しないので、CLI・バッチ・テストからそのまま呼べる。
2. **テストしやすい。** サーバーを立てずに `summarize(ifcopenshell.open("samples/demo-house.ifc"))` で検証できる。
3. **差し替えやすい。** FastAPI を別のフレームワークに変えても、ジョブキューから呼ぶ形に変えても、IFC 層は変えずに済む。

## 3. API の設計

### リソースの考え方

アップロードした IFC を **「モデル」というリソース** として扱い、部材とファイルをその下にぶら下げています。

```
POST /api/models                                 モデルを作る（アップロード＋解析）
GET  /api/models/{modelId}                       モデルの集計
GET  /api/models/{modelId}/elements/{expressId}  モデル内の部材 1 件
GET  /api/models/{modelId}/file                  モデルの元ファイル
```

- **`modelId` はサーバーが発行する推測困難な値**（`uuid4().hex`）。ファイル名を ID にしないことで、同名ファイルの衝突やパス操作の心配をなくしている。
- **部材の ID は expressID をそのまま使う。** 独自 ID を発行しないので、ブラウザ側で得た番号をそのまま URL に入れられる。
- `/api` プレフィックスで統一し、フロントエンドの開発サーバーからプロキシ 1 行で転送できるようにしている。

### 「1 回解析して、何度も問い合わせる」

アップロード時に一度だけ ifcopenshell で開き、**開いたモデル（`ifcopenshell.file`）をメモリに保持** します。
部材クリックのたびにファイルを開き直さないので、属性取得は速く応答できます。
集計（`summarize()`）もアップロード時に一度だけ計算し、`GET /api/models/{modelId}` ではそれを返すだけです。

### レスポンスの形は「フロントの型」と 1 対 1

- キーは **camelCase**（`expressId`, `ifcClass`, `propertySets` …）。Python 側の慣習（snake_case）より、受け取る TypeScript 側の自然さを優先した。
- 形は `frontend/src/types.ts` と 1 対 1 に対応させ、片方だけ変えない（**API の契約**）。
- アップロードのレスポンスには集計に加えて **部材一覧（`elements`）も含める。** 現在の画面では使っていないが、部材一覧・検索・階での絞り込みといった次の機能を API 変更なしで作れるようにしている。
- ifcopenshell が `get_psets()` の結果に付ける内部用の `"id"` キーは、利用者に意味が無いので取り除く。

### ステータスコードの使い分け

| コード | 意味 | 例 |
|---|---|---|
| 400 | 入力の形が不正 | 拡張子が `.ifc` でない |
| 404 | 該当するものが無い | `modelId` が無い／部材が無い／部材ではない（空間など） |
| 413 | 大きすぎる | 500MB 超（Cloudflare 経由の 1 リクエスト 100MB 超は Cloudflare 自身が 413 を返す） |
| 409 | 状態が合わない | 分割アップロードで、全チャンクが揃う前に完了を通知した |
| 422 | 形式は合っているが解析できない | 壊れた IFC・ZIP・HTML など |

エラー本文は FastAPI 標準の `{"detail": "..."}` に統一し、フロントの `handle()` が `detail` をそのまま画面に出せるようにしています。

## 4. 「部材」の範囲：IfcElement に絞る

属性を返すのは **`IfcElement`（壁・床・柱・ドア・窓などの物理的な部材）だけ** です。

- 空間（`IfcSpace`）や建物・階（`IfcBuildingStorey`）は形状を持つことがあっても「部材」ではないので 404 を返す。
- フロントはこれをエラーではなく **「対象外」という正常な状態** として表示する。
- 集計（`elementCount` / `classCounts`）も同じ範囲で数えるので、画面の「部材 n 件」と属性が取れる対象が一致する。

範囲を広げたい場合は、`element_detail()` の `is_a("IfcElement")` 判定と `summarize()` の `by_type("IfcElement")` を **必ずセットで** 変えます。

## 5. 利用者に寄り添うエラー設計

IFC を扱うと「ファイルが開けない」が最も多いトラブルです。そこで、エラーメッセージを **原因 + 対処方法** の形にしています。

```
ifcopenshell.open() を試す
  ├─ 成功 → そのまま使う（下の判定はしない）
  └─ 失敗 → describe_open_error() でファイル先頭 1KB を調べる
            空 / ZIP / UTF-16 / HTML / XML / ISO-10303-21 で始まらない / ヘッダー不正 / その他
```

- **判定は「開けなかったときだけ」行う。** 先に独自チェックで弾くと、ifcopenshell なら読めるファイルまで拒否してしまう恐れがあるため。
- メッセージは日本語で、**何が起きたか** と **どうすればよいか** を必ず書く（例: 「中身がWebページ（HTML）になっています。…元のIFCファイルをダウンロードし直してください（GitHub なら Raw / Download から）」）。
- 失敗したアップロードのファイルはその場で削除する。

新しい判定を足すときも、この順序（開けなかったときだけ判定）と文体を守ります。

## 6. 依存とセットアップを小さく保つ

依存は `fastapi` / `uvicorn[standard]` / `python-multipart` / `ifcopenshell` の 4 つだけです。
DB・キャッシュ・ジョブキューを入れないことで、`pip install -r requirements.txt` と `uvicorn` だけで動きます。
パイロットでは「誰でもすぐ動かせる」ことが、機能の多さより重要だからです。

## 7. 意図的な割り切りと、本番化の差し替えポイント

| 割り切り | 現状の実装 | 差し替えるときの場所 |
|---|---|---|
| 永続化しない | `_models` にメモリ保持（最大 20 件・合計 1000MB、使われていない順に破棄）。再起動で消える | `_get()` / `_register()`（`main.py`）を DB / キャッシュに置き換える |
| 認証しない | `modelId` を知っていれば誰でも参照可 | FastAPI の依存性注入（`Depends`）で全エンドポイントに付ける |
| リクエストの中で解析する | スレッドプールで実行（他の利用者は待たない）。アップロードした本人は解析完了まで待つ | 解析を `ifc_service` のまま、呼び出し側だけジョブ化する |
| ファイルの寿命 = モデルの寿命 | 破棄・再起動と同時に削除 | オブジェクトストレージのライフサイクル管理 |

> 2026-10-03 のレビューを受けて、解析中のブロック（`def` 化）・メモリの上限・サイズの打ち切り・起動時の後始末・モデルごとのロックを入れました。

### 並行アクセスの考え方

- `_models` 自体の出し入れは `_models_lock` で守る（スレッドプールで複数のリクエストが同時に動くため）。
- 同じモデルへの ifcopenshell の呼び出しは、モデルごとの `lock` で 1 つずつにする。ifcopenshell はスレッドセーフを保証していないため。
- 別々のモデルへのアクセスは互いに待たない（ロックはモデル単位）。

**どれも `main.py` 側だけで差し替えられる** ように、IFC 層（`ifc_service.py`）にはこれらの関心を持ち込んでいません。
2026-10-03 のレビューで見つかった問題と、その対応状況は [review-2026-10-03.md](review-2026-10-03.md#バックエンド) にまとめています。

## 8. 拡張するときの手順（設計を崩さないために）

1. **IFC 層に関数を足す**（`ifc_service.py`）。戻り値は JSON にできる値、「無い」は `None`。
2. **HTTP 層にエンドポイントを足す**（`main.py`）。モデル取得は `_get(model_id)`、ステータスコードは 3 節の表に合わせる。
3. **契約を更新する**（`frontend/src/types.ts`）。どの関数・エンドポイントに対応する型かをコメントで書く。
4. **呼び出しを足す**（`frontend/src/api.ts`）。共通の `handle<T>()` を使う。
5. **テストを足す**（`backend/tests/test_backend.py`）。`ifc_service.py` の関数はサーバー無しで試せる。
6. **ドキュメントを更新する**（`backend/README.md` の API 表、`docs/backend.md`）。
