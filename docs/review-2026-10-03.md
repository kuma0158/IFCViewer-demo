# コードレビュー記録（2026-10-03 / Step 5 時点）

対象: `ifc-pilot-step5`（バックエンド: FastAPI + ifcopenshell / フロントエンド: TypeScript（フレームワーク無し）+ Three.js + web-ifc）

## 進め方

- 全ソースを読んだうえで、怪しい箇所は稼働中のサーバー（:8001 / :5173）に実際にリクエストを送って確かめた。
- 各指摘に **確認方法** を付けた。「再現済み」は実際に動かして確かめたもの、「コード上」はコードを読んで確定できるが再現まではしていないもの。
- 重要度: **高** = 公開環境で実害が出うる / **中** = 誤動作・誤表示につながる / **低** = 改善が望ましい
- `docs/backend.md`・`docs/frontend.md` の「注意点・今後の改善候補」に既に書かれている項目は「既知」と付けた。既知でも、公開運用を前提にすると重要度が上がるものはここで評価し直している。

## 前提として重要な点：公開経路

`frontend/vite.config.ts` の `allowedHosts: ['ifc.shinobuabe.com']` から、**Vite の開発サーバーを Cloudflare Tunnel 経由でインターネットに公開している**と読める。
パイロットの割り切り（認証なし・メモリ保持・同期解析）は「手元で使う」前提なら妥当だが、公開すると以下の指摘 B-1〜B-3・F-7 の重要度が上がる。

## バックエンド

### 良い点

- **層の分離が守られている。** `ifc_service.py` は FastAPI を import せず、「見つからない」は `None` を返して `main.py` で 404 に変換している。CLI やテストから再利用しやすい。
- **エラーメッセージが親切。** `describe_open_error()` は ifcopenshell で開けなかったときだけ先頭を調べ、ZIP / UTF-16 / HTML / ifcXML などを原因別に日本語で案内する（壊れたヘッダーで 422 と適切な文言が返ることを再現済み）。
- 失敗時はアップロードしたファイルを確実に削除している（`unlink(missing_ok=True)`）。
- expressID をそのままキーにし、独自の ID 対応表を持たないので、web-ifc 側と自然につながる。

### 指摘

| # | 重要度 | 内容 | 確認方法 |
|---|---|---|---|
| B-1 | 高 | 解析中にサーバー全体が止まる | コード上（既知） |
| B-2 | 高 | 誰でも 100MB までアップロードでき、メモリ・ディスクが際限なく増える | コード上（一部既知） |
| B-3 | 中 | 巨大な expressID で 500 エラー | 再現済み |
| B-4 | 中 | 同じモデルに複数スレッドから同時アクセスしている | コード上（リスク） |
| B-5 | 低 | サーバー再起動で、`uploads/` のファイルが孤児になる | コード上（既知の延長） |
| B-6 | 低 | ポート番号の記載が古い（8000） | コード上 |
| B-7 | 低 | 自動テストが無い | — |

**B-1 解析中にサーバー全体が止まる**（`backend/main.py:49-77`）
`upload_model` は `async def` なのに、中身の `shutil.copyfileobj` と `ifcopenshell.open` / `summarize` はすべて同期処理。async 関数内の同期処理はイベントループそのものを止めるので、大きな IFC の解析中は **他の利用者の属性取得や IFC ダウンロードも含め、すべてのリクエストが待たされる**。
対処: `def upload_model(...)` に変える（FastAPI がスレッドプールで実行する）のが最小の修正。将来は解析をバックグラウンドジョブ化する。

**B-2 誰でも 100MB までアップロードでき、メモリ・ディスクが際限なく増える**（`main.py:39, 54-61, 76`）
- `_models` に解析済みの ifcopenshell モデルを保持し続け、件数の上限も削除もない。ifcopenshell のモデルは元ファイルより大きなメモリを使うことが多いので、アップロードを繰り返すとプロセスのメモリが増え続ける（既知の「永続化なし」とは別の問題）。
- サイズ上限のチェックは全部書き込んだ後（既知）。`Content-Length` も見ていないので、100MB を超えるファイルでも一度は全部受信してディスクに書く。
- 認証が無い（既知）ので、公開環境では第三者がこれを繰り返せる。
対処: `_models` に件数上限か、最終アクセスからの有効期限を設けて古いものから捨てる（ファイルも一緒に削除）。書き込み中に累積サイズを数えて上限で打ち切る。公開するなら、最低限 Cloudflare Access などで利用者を絞る。

**B-3 巨大な expressID で 500 エラー**（`ifc_service.py:190-195`）
`GET /api/models/{id}/elements/99999999999` → **500 Internal Server Error**（再現済み）。ログは `OverflowError: in method 'file_by_id', argument 2 of type 'int'`。`element_detail` は `RuntimeError` しか捕まえていない。
対処: `except (RuntimeError, OverflowError)` にする。またはパスパラメータを `express_id: int = Path(ge=1, le=2**31 - 1)` で制限して 422 にする。

**B-4 同じモデルに複数スレッドから同時アクセスしている**（`main.py:86-92`）
`get_element` は同期関数なのでスレッドプールで並行実行され、同じ ifcopenshell モデルを複数スレッドから同時に読む。ifcopenshell はスレッドセーフを保証していない。パイロットの利用規模では問題が出にくいが、公開して同時アクセスが増えると、まれに不正な結果やクラッシュになりうる。
対処: モデルごとに `threading.Lock` を持ち、`element_detail` の呼び出しを囲む。

**B-5 サーバー再起動で、`uploads/` のファイルが孤児になる**
`_models` はメモリにしかないので、再起動するとファイルとモデル ID の対応が失われ、`uploads/` のファイルは二度と使われないまま残る（「ファイルの後始末」が既知だが、再起動時に必ず孤児になる点は書かれていない）。
対処: B-2 の破棄処理と合わせて、起動時に `uploads/*.ifc` を削除する（再起動で消える仕様と揃える）。

**B-6 ポート番号の記載が古い**
`main.py:11-12` の docstring、`backend/README.md`、`docs/backend.md`（CORS の説明・セットアップ）が 8000 のまま。実際は 8001（8000 は別プロジェクトが使用）。

**B-7 自動テストが無い**
`ifc_service.py` は HTTP に依存しない純粋な関数なので、`samples/demo-house.ifc` を使った pytest を少数書くだけで、`summarize` / `element_detail` / `describe_open_error` の回帰を防げる。B-3 のような境界値もここで押さえられる。

## フロントエンド

### 良い点

- **層の分離が Step 4 と同じ水準で保たれている。** `IfcViewer` は API を知らず、入力はメソッド、出力はコールバック。`ifcLoader.ts` は DOM に依存しない。
- **XSS への備え。** `lib/dom.ts` は文字列を必ずテキストノードとして入れ、innerHTML を使わない。部材名・プロパティ値は IFC の作成者が自由に書ける値なので重要。
- 依存が three / web-ifc の 2 つだけになり、`tsc --noEmit` がそのまま型チェックとして使える。
- Three.js / web-ifc のメモリ解放（`g.delete()`、`CloseModel` の try/finally、`dispose()`）が丁寧。

|---|---|---|---|
| F-1 | 中 | 素早く 2 つの部材をクリックすると、ハイライトと属性パネルが食い違うことがある | コード上 |
| F-2 | 中 | 通信エラーやサーバーエラーも「対象外です」と表示される | コード上 |
| F-3 | 中 | 3D の読み込みに失敗すると、ステータスが「サーバーで解析中…」のまま残る | コード上 |
| F-4 | 低 | 読み込みの競合（既知）・web-ifc の二重初期化 | コード上（一部既知） |
| F-5 | 低 | ファイル選択ボタンをキーボードで操作できない | コード上 |
| F-6 | 低 | マテリアルの破棄漏れ（既知）・バンドルが 4MB | ビルド出力で確認 |
| F-7 | 中 | Vite の開発サーバーをそのまま公開している | 設定から |

**F-1 素早く 2 つの部材をクリックすると、ハイライトと属性パネルが食い違うことがある**（`frontend/src/app.ts` の `onSelect`）
部材 A → B と続けてクリックしたとき、A の `fetchElement` の応答が B より後に返ると、**ハイライトは B なのにパネルは A の属性**になる。別モデルをアップロードした直後に、前のモデルへの応答が遅れて届いた場合も同じ。
対処: 呼び出しごとに番号を振り（`const seq = ++selectSeq`）、応答時に `seq !== selectSeq` なら捨てる。

**F-2 通信エラーやサーバーエラーも「対象外です」と表示される**（`app.ts` の `onSelect` の `catch`）
すべての例外を `{ notFound: true }` に変換しているので、ネットワーク断・500（B-3 など）・モデル消失（サーバー再起動後の 404「モデルが見つかりません」）でも「#123 は属性表示の対象外です」と表示され、原因が分からない。
対処: `api.ts` の `handle()` で HTTP ステータスを持つエラー型を投げ、「部材が見つかりません（404）」のときだけ対象外とし、それ以外は赤帯にメッセージを出す。サーバー再起動でモデルが消えた場合は「もう一度ファイルを開いてください」と案内する。

**F-3 3D の読み込みに失敗すると、ステータスが「サーバーで解析中…」のまま残る**（`app.ts` の `onError` / `onFileChange`）
アップロード成功後に web-ifc 側で失敗すると、赤帯にエラーは出るが、ヘッダーのステータスは「サーバーで解析中…」のまま変わらない。また `state.model` は新しいモデルに更新済みなのに、画面には前のモデルの 3D が残る（`load` は失敗時に `clearModel()` しない）。
対処: `onError` で `state.status` を更新する。失敗時に前のモデルを消すか、`state.model` を戻す方針を決める。

**F-4 読み込みの競合（既知）・web-ifc の二重初期化**（`viewer/IfcViewer.ts` の `load` / `getIfcApi`）
既知の「後から終わった方が表示される」に加え、最初の初期化が終わる前に 2 回 `load` が走ると、`IfcAPI` が 2 つ作られて WASM を 2 回初期化する。
対処: `getIfcApi` は Promise をキャッシュする（`this.ifcApiPromise ??= init()`）。`load` は F-1 と同じ番号方式で古い結果を捨てる。

**F-5 ファイル選択ボタンをキーボードで操作できない**（`style.css` の `.upload input { display: none }`）
`display: none` の input はタブ移動の対象から外れるので、キーボードだけではファイルを選べない（Step 4 から引き継いだ問題）。
対処: 見た目だけ隠す CSS（`position: absolute; opacity: 0; width: 1px; height: 1px` など）にし、`:focus-visible` で label に枠を出す。

**F-6 マテリアルの破棄漏れ（既知）・バンドルが 4MB**
- `clearModel()` はジオメトリのみ破棄（既知）。マテリアルは `ifcLoader.ts` 内のキャッシュ単位なので、Group の Mesh から重複なく集めて `dispose()` すればよい。
- `vite build` の出力が 1 ファイル 4,073KB（gzip 526KB）で、Vite が 500KB 超の警告を出す。大半は three と web-ifc。`IfcViewer` を `import()` で遅延読み込みにすると、最初の画面表示が速くなる。

**F-7 Vite の開発サーバーをそのまま公開している**（`vite.config.ts` の `allowedHosts`、`scripts/start-servers.ps1`）
開発サーバーは本番配信用ではない（ソースマップ・未圧縮モジュールの配信、HMR 用の WebSocket、開発サーバー自体の脆弱性への露出）。公開を続けるなら、`npm run build` の `dist/` を配信する構成（`vite preview`、または FastAPI の `StaticFiles` で `dist/` と `/api` を同じポートで配信）に切り替えるのが望ましい。
