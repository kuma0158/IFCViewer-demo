# フロントエンドの設計思想（TypeScript + Three.js + web-ifc／フレームワーク無し）

全体の設計思想は [design-philosophy.md](design-philosophy.md)、ファイル・関数単位の解説は [frontend.md](frontend.md) を参照してください。
このドキュメントは、フロントエンドが **なぜこの形になっているか** を掘り下げたものです。

## 1. フロントエンドの役割：「形状」と「見せ方」

| フロントエンドがやること | フロントエンドがやらないこと |
|---|---|
| IFC をアップロードする | 属性・集計の計算（サーバーの ifcopenshell が正本） |
| web-ifc で IFC から三角形メッシュを作る | 部材 ID の対応表を持つ（expressID をそのまま使う） |
| Three.js で表示・視点操作・クリック判定・ハイライト | |
| 属性を日本語ラベル付きで見やすく表示する | |

**形状はブラウザで作り、属性はサーバーに聞く。** この 2 つを expressID でつなぐのがフロントエンドの仕事です。

## 2. なぜフレームワークを使わないのか（Step 5 の判断）

Step 4 までは Vue 3 を使っていましたが、Step 5 で撤去し、**DOM API を直接使う純粋な TypeScript** にしました。

### 判断の理由

1. **画面が小さい。** UI はヘッダー（ボタン・ステータス）、エラー帯、属性パネルの 3 つだけ。状態も 5 項目しかなく、リアクティブな仕組みの恩恵が小さい。
2. **複雑さの中心は 3D 側にある。** Three.js と web-ifc はもともと命令的（「作る → 追加する → 破棄する」）な API で、Vue のコンポーネントの中でもほぼ素の TypeScript として書かれていた。フレームワークが肩代わりしていた部分は少なかった。
3. **依存とツールを減らせる。** `vue` / `@vitejs/plugin-vue` / `vue-tsc` が不要になり、型チェックは標準の `tsc` だけ。vue-tsc の都合で TypeScript のバージョンを縛られることもなくなった。
4. **動きが追いやすい。** いつ DOM が書き換わるかがコードにそのまま書いてあり、パイロットの「読んで理解できる」という優先順位に合う。

### 引き換えにしたもの

- 状態を変えたら **自分で `render*()` を呼ぶ** 必要がある（自動追跡しない）。
- 画面が大きくなる（一覧・フィルター・複数パネルなど）と、手書きの描画コードは増えていく。

> 画面が大きく育った場合は、フレームワークの再導入を検討します。ただし、層の分離（4 節）を守っていれば、`app.ts` を差し替えるだけで済み、ビューア・変換・通信はそのまま使えます。再導入は利用者と合意してから行います。

なお **Vite は引き続き使っています。** フレームワークではなく、開発サーバー（プロキシ・即時反映）とバンドラーとしての利用です。

## 3. 構成と依存の向き

```
main.ts ──▶ app.ts ──┬──▶ api.ts ──▶ types.ts
                     ├──▶ lib/ifcLabels.ts
                     ├──▶ lib/dom.ts
                     └──▶ viewer/IfcViewer.ts ──┬──▶ lib/ifcLoader.ts ──▶ web-ifc, three
                                                ├──▶ lib/dom.ts
                                                └──▶ three（OrbitControls）
```

**依存は上から下への一方向** です。下の層は上の層を知りません。

| モジュール | 知っていること | 知らないこと |
|---|---|---|
| `app.ts` | 画面の状態、API、ビューアの使い方 | Three.js・web-ifc の詳細 |
| `viewer/IfcViewer.ts` | Three.js、web-ifc の初期化、DOM の自分の領域 | **API（`api.ts`）・属性の取り方・画面の他の部分** |
| `lib/ifcLoader.ts` | web-ifc の出力形式、Three.js のメッシュ | **DOM・画面** |
| `api.ts` | URL と HTTP、エラーの読み方 | 画面 |
| `types.ts` | バックエンドとの契約 | 実装 |

この向きを守っているので、たとえば

- 属性をサーバーではなく別の手段で取るようにしても、**ビューアは変えずに済む。**
- ビューアを別の 3D ライブラリに替えても、**画面と API は変えずに済む。**
- `ifcLoader.ts` は DOM を使わないので、将来 Web Worker に移して重い変換をバックグラウンドで行うこともできる。

## 4. ビューアは「部品」として作る

`IfcViewer` は、Vue コンポーネントの代わりに **クラス** として作っています。

```ts
const viewer = new IfcViewer(container, {   // 置き場所と、通知の受け取り先を渡す
  onLoaded: ({ meshCount }) => { ... },
  onSelect: (expressID) => { ... },          // 空クリックは null
  onError: (message) => { ... },
})
await viewer.load(url)        // 入力はメソッド
viewer.highlight(expressID)
viewer.dispose()              // 後始末も明示的に
```

| Vue 版（Step 4） | TypeScript 版（Step 5） | 理由 |
|---|---|---|
| props `fileUrl` を watch | `load(url)` メソッド | 「いつ読み込むか」を呼び出し側が明示的に決められる |
| emit `select` / `loaded` / `error` | コンストラクタで受け取るコールバック | 受け取り手は常に 1 つ。型が付き、仕組みが単純 |
| `defineExpose({ highlight })` | 公開メソッド `highlight()` | クラスの public / private がそのまま公開範囲になる |
| `onBeforeUnmount` | `dispose()` | 解放の責任をはっきりさせる |

### 後始末を設計に含める

3D は GPU やWebAssembly のメモリを使うので、**作ったものは必ず解放する** ことを設計の一部にしています。

- ジオメトリ・マテリアル（共有されているので重複なく集める）・ハイライト用マテリアル・レンダラー・OrbitControls は `dispose()`。
- web-ifc のジオメトリは `g.delete()`、モデルは `try/finally` で必ず `CloseModel`。
- イベントリスナーは **アロー関数のプロパティ** として登録し、同じ参照で `removeEventListener` できるようにしている。
- `ResizeObserver` は `disconnect()`、描画ループは `setAnimationLoop(null)`。

## 5. 画面の状態と描画

### 状態は 1 か所に集める

```ts
interface AppState {
  model: ModelSummary | null
  element: ElementDetail | NotFoundElement | null
  status: string
  error: string
  uploading: boolean
}
```

画面に関わる状態はすべて `state` にあります。DOM に状態を持たせない（DOM から値を読み戻さない）ことで、「今どういう状態か」は `state` を見れば分かります。

### 状態は型で表す

選択中の部材は **判別可能な共用体** で表しています。

| 値 | 意味 | 表示 |
|---|---|---|
| `null` | 未選択 | 「部材をクリックすると…」 |
| `NotFoundElement` | 形状はあるが部材ではない（空間など） | 「#123 は属性表示の対象外です」 |
| `ElementDetail` | 属性あり | 基本情報とプロパティセット |

`renderSide()` で `'notFound' in element` と判定すると、それ以降は TypeScript が `ElementDetail` として扱ってくれるので、表示の分岐漏れや取り違えを型チェックで防げます。

### 描画は 2 種類のやり方を使い分ける

| 部分 | やり方 | 理由 |
|---|---|---|
| 骨組み（ヘッダー・エラー帯・パネルの枠・ビューア） | `mountApp()` で **一度だけ作る** | ビューアの canvas やファイル入力を作り直すと、3D の状態や入力が失われるため |
| ヘッダー・エラー帯 | `renderHeader()` で **既存要素の中身だけ書き換える** | 要素数が固定で、書き換える箇所が決まっているため |
| 属性パネル | `renderSide()` で **毎回まるごと作り直す** | 中身の構造が状態によって大きく変わる。量も少ないので、差分を取るより作り直す方が単純で確実 |

仮想 DOM のような差分計算は持ちません。この規模では「作り直す」で十分速く、コードも短く済みます。

### DOM は `el()` で組み立てる

```ts
el('dl', { class: 'basic' },
  el('dt', {}, '名前'),
  el('dd', {}, formatValue(element.name)),
)
```

- HTML テンプレートに近い入れ子の形で書けるので、構造が読み取りやすい。
- 子に `false` / `null` を渡すと無視されるので、`cond && el(...)` で条件付き表示が書ける。
- **文字列は必ずテキストノードとして入れ、`innerHTML` を使わない。** 部材名やプロパティ値は IFC の作成者が自由に書ける値であり、HTML として解釈させると XSS（スクリプトの埋め込み）の入口になるため。これは Vue のテンプレートが自動でしていたエスケープを、`el()` が肩代わりしている。

### 非同期の応答は「最新かどうか」を確かめてから反映する

属性の取得（`fetchElement`）と 3D の読み込み（`load`）は、どちらも **後から始めたものが先に終わることがある** 処理です。
そこで、呼び出しごとに番号を振り、応答が届いた時点で最新の番号でなければ捨てます（`selectSeq` / `loadSeq`）。

```ts
const seq = ++selectSeq
const element = await fetchElement(...)
if (seq !== selectSeq) return   // より新しい選択が始まっていれば捨てる
```

AbortController で通信を取り消す方法もありますが、web-ifc の変換は途中で止められないので、両方に同じ仕組みが使える番号方式にしています。

### エラーは「対象外」と区別する

部材ではないもの（空間など）の 404 は **正常な状態**（「対象外です」）、それ以外は **エラー**（赤帯）として扱います。
`api.ts` の `ApiError` が HTTP ステータスを持っているので、この区別ができます。
サーバーの再起動でモデルが消えた場合は「もう一度IFCファイルを開いてください」と、利用者が次に何をすればよいかを示します。

## 6. 3D 表示の設計

### 1 部材 = 1〜複数の Mesh、目印は expressID

web-ifc は部材ごとに「配置済みのジオメトリ」を 1 つ以上返します。それぞれを 1 つの `THREE.Mesh` にし、**`mesh.userData.expressID` に部材の番号を記録** します。

- クリック判定（Raycaster）で当たった Mesh から、すぐに expressID が分かる。
- 1 部材が複数の Mesh に分かれていても、同じ expressID を持つ Mesh をまとめて扱える（ハイライト）。

メッシュのマージやインスタンシングで高速化する場合も、**クリック位置から expressID を引ける仕組みは必ず残す** のがルールです（この番号が形状と属性をつなぐ唯一のキーなので）。

### 見た目のための小さな工夫

| 工夫 | 理由 |
|---|---|
| 同じ色のマテリアルを使い回す（色をキーにキャッシュ） | マテリアル数を減らし、描画を軽くする |
| 半透明（窓ガラスなど）は `transparent` / `opacity` を設定 | IFC の色情報をそのまま反映する |
| `side: DoubleSide` | 法線の向きが揃っていない IFC でも面が消えない |
| ハイライト用マテリアルに `polygonOffset` | 隣の部材と面が重なる箇所で、選択色が確実に手前に見える（Z ファイティング対策） |
| `fitCamera()` で `near` / `far` をモデルの大きさから決める | 小さな家具から大きな建物まで、切れずに表示できる |

### 操作感

- **ドラッグとクリックを区別する。** 押した位置と離した位置が 4px 未満のときだけ「クリック」とみなし、視点を回したつもりで部材が選ばれてしまうのを防ぐ。
- **空クリックで選択解除。** 何もない所をクリックすると `null` を通知し、パネルも未選択に戻る。

### web-ifc は一度だけ初期化する

WebAssembly の初期化は重いので、最初の読み込み時に 1 回だけ行い、以降は使い回します。
`web-ifc.wasm` は `npm install` 時に `public/` へ自動コピーし、サイトのルートから配信しています（手作業を無くすため）。

## 7. バックエンドとの付き合い方

- **同一オリジンに見せる。** 開発時は Vite のプロキシで `/api` を FastAPI（:8001）へ転送するので、コードには相対パス `/api/...` しか出てこない。ホスト名や CORS を意識しない。
- **API の型は `types.ts` に集約する。** `backend/ifc_service.py` の戻り値と 1 対 1 で対応させ、キー名の書き間違いは型チェックで見つける。
- **エラーは `detail` をそのまま見せる。** サーバー側で「原因 + 対処方法」の日本語メッセージを作っているので、フロントは加工せずに赤帯へ出す。
- **ファイル本体はビューアが直接取りに行く。** `app.ts` は URL を作って渡すだけで、IFC のバイト列には触らない。

## 8. TypeScript の使い方

- `strict: true` に加え、`noUnusedLocals` / `noUnusedParameters` / `noFallthroughCasesInSwitch` / `verbatimModuleSyntax`。
- 型だけの import は `import type`（ビルド時に確実に消えるようにするため）。
- `any` は使わず、中身が決まらない値は `unknown`（プロパティ値など）。
- `npm run build` は `tsc --noEmit` が通らなければビルドしない。**型エラーのあるコードは配布されない。**

## 9. 意図的な割り切りと、改善の方向

| 割り切り | 現状 | 改善の方向 |
|---|---|---|
| 二重の解析 | 同じ IFC をサーバーとブラウザで 1 回ずつ解析 | 単純さを優先。大きなファイルで問題になれば見直す |
| 描画の最適化なし | 1 部材 1〜複数 Mesh で描画コールが多い | ジオメトリのマージ・インスタンシング（expressID を引ける仕組みは残す） |
| 変換はメインスレッド | 大きな IFC では変換中に画面が固まる | `ifcLoader.ts` を Web Worker へ移す（DOM 非依存なので移しやすい） |
| 1 ファイル 4MB のバンドル | three・web-ifc を最初にまとめて読む | `IfcViewer` を `import()` で遅延読み込み |
| 本番配信は `vite preview` | `dist/` を 5173 番で配信（トンネルの転送先を変えないため） | 利用者が増えたら FastAPI の `StaticFiles` や静的ホスティングで配信 |

## 10. 拡張するときの指針

- **ビューアに機能を足す**（例: 部材の表示／非表示、断面）: `IfcViewer` に公開メソッドを足し、通知が必要なら `IfcViewerEvents` にコールバックを足す。`app.ts` 側でつなぐ。ビューアから `api.ts` は呼ばない。
- **画面に部品を足す**（例: 部材一覧）: `app.ts` の `state` に項目を足し、対応する `render*()` を作る。一覧の行クリックで `viewer.highlight(expressId)` を呼べば、3D と連動する。部材一覧のデータはアップロード時のレスポンス（`state.model.elements`）に既にある。
- **日本語ラベルを足す**: `lib/ifcLabels.ts` の辞書に追記するだけ。関数は変えない（辞書に無い名前は英語のまま出るフォールバックを保つ）。
- **文字を表示する**: 必ず `el()` / テキストノード経由で。`innerHTML` は使わない。
